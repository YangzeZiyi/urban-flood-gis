# 城市内涝风险可视化平台

> Urban Flood Risk Visualization Platform
> 基于 Vue3 + Cesium + Spring Boot + PostGIS 的城市内涝风险三维可视化与预警系统

---

## 这个项目是什么

把「数据采集 → 空间分析 → 风险建模 → 三维可视化」串成一条完整链路，展示某城市在不同降雨情景下的内涝风险分布，支持时间轴回放与点位查询。

**技术骨架**沿用本科毕业设计《基于 SharpMap 的 PM2.5 信息管理系统》的思路，技术栈整体替换为 2026 年主流方案，场景升级为更有现实价值的城市韧性方向。

**完整设计见 [`docs/项目说明.md`](docs/项目说明.md)**：系统组成、数据流、算法取舍、验证方式、已知局限。

## 快速开始

### 1. 环境准备

见 `docs/教程/PostgreSQL安装图解教程.html`（数据库）与 `docs/环境与路径规划.md`（工具版本、安装路径、C 盘保护）。

**所有工具装在 D 盘，不占 C 盘空间：**

| 工具 | 安装路径 |
|---|---|
| PostgreSQL 18 | `D:\dev\PostgreSQL\18` |
| Python 3.13 | `D:\dev\Python313` |
| Node.js | `D:\dev\nodejs` |
| Git | `D:\dev\Git` |
| JDK 21 | 已装（Microsoft 版，保持原位） |
| IDEA / VS Code | `D:\dev\JetBrains` / `D:\dev\VSCode` |

### 2. 初始化数据库

```bash
psql -U postgres -c "CREATE DATABASE floodgis;"
psql -U postgres -d floodgis -c "CREATE EXTENSION postgis;"
psql -U postgres -d floodgis -f sql/01_schema.sql
```

### 3. 启动

```bash
# 后端（8080）
cd backend && mvnw spring-boot:run

# 前端（5173，/api 代理到后端）
cd frontend && npm run dev
```

浏览器打开 **http://127.0.0.1:5173**

> 别用 `localhost`：天地图 key 的域名白名单只登记了 `127.0.0.1`，换成 `localhost` 会整片返回 403，现象是底图消失、只剩一个蓝色地球。

### 4. 不装环境也能看

`scripts/启动演示.bat` 直接起打包好的演示服务（jar 内已含前端），只要本机有 JDK 21 和 PostgreSQL。使用与排错见 `scripts/演示包说明.txt`。

### 5. 在线版（静态数据）

**https://wuhan-flood-risk.app.workbuddy.host/?sharecode=BL3KKABM4Y**

线上没有 JVM，也没有 PostgreSQL，所以跑的是「静态数据版」：五个接口换成导出好的文件，
点查按 0.1° 分块读 `.bin`，框选统计在浏览器里算。同一套 Vue 代码，构建时用
`VITE_STATIC_DATA=1` 切分支（判断收在 `frontend/src/api.js` 一个文件里）。

```bash
cd pipeline && python publish/export_static.py   # 导出到 frontend/public/static-data（24 MB）
cd frontend && npm run build:static              # 产物 dist/，丢给任意静态服务器
node scripts/verify-static.mjs                   # 和后端逐格对账，需要后端在跑
```

静态版与后端的一致性：单点查询行列号与等级 100% 相同，框选统计的参与评价面积、
均值、无数据格数与后端完全一致，分档占比差 ≤0.5 个百分点（量化到 1/254 导致）。

### 6. 演示视频

另有一支 75 s / 1920×1080 / 25 fps 的演示片（无音轨，信息靠画面，不用音乐盖）。

八段分镜覆盖「标题 → 算法链 → 静态指数 → 三维界面 → 逐日时间轴 → 框选统计 → 验证 → 结尾」，
其中逐日时间轴那 20 秒是全片唯一数据在动的段落：153 帧汛期风险配着雨量、API、
极高风险面积三个读数一起变。

它不录屏，是逐帧合成的：`frame_at(t)` 是一个纯函数，给定时间就能算出该画哪一帧，
同一份输入永远产出同一支片子（重跑校验过 md5，一字节不差）。正因为它完全由数据决定，
片子里不会出现"演示比实际好看"的落差 —— 时间轴的底图和前端读的是同一次导出的同一份网格。

生成脚本 1200 余行，与 GIS 主线无关，作为本地工具保留、不随仓库发布；成片 14 MB 同理。
仓库里只留这条记录，方便日后回看它讲过什么。

## 数据来源

| 数据 | 来源 | 说明 |
|---|---|---|
| DEM 高程 | Copernicus DEM GLO-30 | 欧空局 2020 发布，AWS 开放数据托管，免费免 key，1″ 格网（约 30 m） |
| 日降雨 | Open-Meteo Archive（ERA5 再分析） | 免费免 key，取武汉 5 个格点 2017–2024 逐日序列 |
| 行政区边界 | 阿里云 DataV.GeoAtlas | adcode 420100 含下级区县，标准 GeoJSON |
| 易涝点 | 武汉市水务局《中心城区易渍水点风险图》（2020-05） | 59 处中地名可定位的 40 处入库，坐标手工定位，精度约 ±300 m |
| 影像底图 | 天地图 | 个人实名 key，需把访问域名加进白名单 |

### 底图与各图层的性质

**底图**：天地图（国家地理信息公共服务平台）的影像层 `img_w` + 影像注记层 `cia_w`，
走 WMTS，浏览器端 key。选它有两个实际原因：坐标系是 CGCS2000，与库里的 WGS84
差异在厘米级，易涝点能严丝合缝压在地物上；换成高德/腾讯（GCJ-02）会整体偏移几百米，
那种偏移在 1:5000 的视图下一眼就能看出来。

底图不可用时（key 过期、域名没进白名单）会**自动降级**成随包发布的 Cesium
NaturalEarthII 离线影像，页面不会变成一个光秃秃的蓝色球，控制台同时给出原因。

**压在底图上面的三层，性质各不相同**：

| 图层 | 性质 |
|---|---|
| 区县边界 | 阿里云 DataV 公开 GeoJSON，仅用于定位，不作为法定界线 |
| 易涝点（40 个） | 武汉市水务局 2020 年公开发布的易渍水点清单，坐标手工定位，±300 m |
| 易涝指数贴图 | **本项目自己算的**：公开 DEM 派生坡度/汇流/填深，加权成分位数分级 |

**所以它是什么**：一个用公开数据复现「地形 + 降雨 → 易涝可能性」的技术演示。
**它不是什么**：不是实测积水深度，不是官方预警，不能用于防汛决策；也不是测绘成果——
底图由天地图提供（其服务本身经过审核），但本项目叠加的专题图层没有送审，
因此不对外提供地图服务、不用于商业用途。页面上那句话不是免责套话，是这个页面的定位。
