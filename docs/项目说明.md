# 城市内涝风险可视化平台 · 项目说明

> 把「数据采集 → 地形分析 → 风险建模 → 三维可视化」做成一整条可复现的链路，
> 在三维地球上展示武汉在不同降雨情景下的内涝风险分布，支持汛期逐日回放、
> 点位查询与区域统计。

本文是项目的总说明：讲清系统由什么组成、数据怎么流、每个决定为什么这么定、
结果怎么验证、以及目前还差在哪。更细的内容分散在 `docs/` 下，文末有索引。

## 三、数据流

```
Copernicus GLO-30 分幅（9 幅 1°×1°）
  └─ 拼接裁剪 → 重投影 EPSG:4547 → data/processed/dem/wuhan_dem_cgcs2000.tif (5162×4440)

阿里云 DataV 行政边界（420100_full）
  └─ 入库 admin_boundary（市 + 13 区）

Open-Meteo Archive（ERA5，5 个格点，2017–2024）
  └─ 入库 rain_station / rain_record（14,610 条）

DEM
  ├─ 填洼（Priority-Flood）→ 填深栅格
  ├─ 坡度（Horn 3×3）→ 坡度栅格
  └─ 汇流累积（D8）→ 汇流栅格
        ↓
   四因子加权 → 易涝指数 → 水体掩膜 → 分位数分级
        ↓
   ├─ 贴图 PNG（EPSG:4326 等经纬度网格）→ 前端 SingleTileImageryProvider
   └─ 点击网格 .bin（4 通道 float32）→ 后端按行列定位读

降雨序列 + 马尔科夫链
  └─ 逐日风险系数 × 静态指数 → 153 帧动态风险（WebP + 分级 bin）
```

关键约定：**贴图、点击网格、分级阈值三者同源**，都用同一个 EPSG:4326 等经纬度网格，
所以「图上看到的颜色」和「点一下查到的数值」不会打架。市域外与水体在点击网格里写 `NaN`，
不是 0——「没有数据」和「风险很低」是两件事。

## 四、数据来源与口径

| 数据 | 来源 | 分辨率 / 范围 | 说明 |
|---|---|---|---|
| 高程 | Copernicus DEM GLO-30 | 1″（约 30 m），EGM2008 高程基准 | 欧空局 2020 发布，AWS 开放数据托管，免费免 key |
| 行政区边界 | 阿里云 DataV.GeoAtlas | 市 + 13 区 | 简化轮廓，可视化级精度（百米级），非测绘成果 |
| 日降雨 | Open-Meteo Archive（ERA5 再分析） | 5 个格点，逐日 | 免费免 key；2015–2016 两年接口仍是 0.25° 粗网格，故序列从 2017 起 |
| 易涝点 | 武汉市水务局《中心城区易渍水点风险图》（2020-05） | 59 处中 40 处 | 地名可定位的 40 处，坐标手工定位，精度约 ±300 m，已用 `ST_Contains` 校验行政区 |
| 影像底图 | 天地图 | 影像 + 影像注记 | 个人实名 key，需把访问域名加入白名单 |

**DEM 用的是 DSM 而不是 DTM**——它带着建筑和树冠的高度，城区高程与坡度会系统性偏高。
这一点没有回避，直接列进第七节。

## 五、算法链

### 5.1 填洼：为什么必须做，且必须带 ε

Priority-Flood（Barnes 2014）：边界像元入小顶堆，从最低处向内陆漫，遇到比水位低的邻居
就把它垫到水位高一点点，差额就是填深。

出流时加一个极小的 ε 是关键补丁：填完之后大片区域是绝对平面，D8 在平面上八个邻居一样高，
分不出上下游，汇流会在那里断掉。ε 大到能让浮点数分出先后，小到不影响坡度即可。

产物填深栅格是后面判水的主要依据——湖是封闭盆，要填；沿江平地是斜的，填深接近 0。

### 5.2 坡度与汇流

- 坡度：3×3 Horn 算子，输出角度
- 汇流：D8 单流向，按汇水面积累积

武汉全域坡度 <1° 的面积占 45.7%，这是内涝的地形基础；汇流最大值 21,449,470，
94.6% 的像元最终汇到同一个出口。

### 5.3 易涝指数：四因子加权

各因子先按分位数截断并归一化到 0~1，再加权：

| 因子 | 方向 | 权重 | 归一化区间 |
|---|---|---|---|
| 高程 | 越低越危险 | 0.20 | p2 ~ p75 |
| 坡度 | 越平越危险 | 0.15 | p25 ~ p90 |
| 填深 | 越深越危险 | 0.15 | p50 ~ p98 |
| 汇流 | 越大越危险 | 0.50 | log 后 p25 ~ p99 |

**权重是人拍的，所以必须做敏感性分析**：固定因子只换权重，比较三套方案。
Spearman 秩相关 0.968~0.998，「极高」前 3% 的重合率 67.4%（平权）~ 82.5%（地形主导）。
结论是：整体排序稳，顶档会换掉三分之一，因此只能声明「相对风险排序」，
不能声称某块地「一定会淹」。

### 5.4 水体掩膜：相对地形判据

任何地形汇水算法都会把湖心、江心排在最前面——它们本来就是水的终点。实测指数 ≥ 0.83
的像元里 77% 是水面，不剔掉就是循环论证。

判据不引外部水体数据，只用 DEM 自己的形状：

```
candidate = (坡度 < 0.1°) & (填深 > 3 m) & (高程 < 35 m)
再按 8 邻域连通域，剔掉面积 < 1.0 km² 的小块
```

- **坡度** 挡「看起来平但其实不是盆」的地方，水面实测全 0.000°
- **填深** 挡沿江平地（填深 0.00 m）和建筑围成的假碗；不能卡太高，东湖湖心只有 4.79 m
- **高程** 挡山区假湖（黄陂有个 29 km²、61.6 m 的洼地不是水）
- **面积 1.0 km²** 挡院子、楼间空地——但**不能更小**：封闭小洼地恰恰是内涝点本身

面积门槛最初定 0.3 km²，结果 40 个官方易涝点里有 3 个被判成水面、拿不到指数。
逐点量连通域面积才看清：玉龙路邹家大湾 0.583、竹叶山立交 0.325、南湖路供销学校 171.99，
而真湖最小也有 11.35 km²。小洼地（0.3~0.6）和真湖（11+）之间空着一个数量级，
门槛提到 1.0 两头都保住：陆地 7,077 → 7,118 km²，湖心与江心采样点仍全部判为水。

试过另一条路——收紧填深来区分。实测填深 > 3.5 m 就误删南湖，> 4.0 m 一片真湖掉队，
水体从 1,455 掉到 1,088 km²。填深这个维度上「真湖」和「封闭洼地」本来就分不开
（玉龙路 3.73 vs 沙湖 4.80），能分开它们的只有面积。

### 5.5 分级：为什么不用固定阈值

第一版用 0.65 当「极高」，算出 5,119 km²，占全市 60%——一张把六成城区标红的图等于没说。
改成按陆地指数分位数切：

| 等级 | 分位 | 面积 |
|---|---|---|
| 低 | 后 35% | 2,491 km² |
| 较低 | 35~65% | 2,135 km² |
| 中 | 65~88% | 1,637 km² |
| 高 | 88~97% | 641 km² |
| 极高 | 前 3% | 214 km² |

代价是换一套权重边界会动，两版结果不能逐像素比较。要发论文得用实测渍水点标定绝对阈值，
本项目没有，所以只声明相对风险。

### 5.6 动态风险：降雨 → 系数 → 逐日风险

1. **降雨五态马尔科夫链**：日雨量分 无雨/小雨/中雨/大雨/暴雨，统计转移矩阵，按行归一化
2. **前期降雨指数（API）**：`api_t = api_{t-1} × 0.9 + 当日雨量`，刻画土壤湿润程度
3. **放大系数**：API ≤ 30 mm 不放大（系数 1.0），API ≥ 500 mm 放大到顶（系数 2.0），中间线性过渡
4. **合成**：`risk = min(index × factor, 1)`，factor = 1 时严格等于静态指数
5. **出图**：逐日一帧，`153 帧`覆盖整个汛期

峰值出现在 2020-07-07（当日 5 站雨量 84.7~171.7 mm）：极高风险 1,890.7 km²、高风险 990.0 km²。

选 500 mm 作定标点、系数上限取 2.0，都是「能自圆其说」而非「准」——它本质是在说
「饱和土壤把致涝机会放大了几倍」，没有实测渍水点做标定，这是已知缺口。

## 六、可视化与交互

| 能力 | 实现要点 |
|---|---|
| 三维底图 | 天地图影像 + 影像注记两层；每加一个影像层都要 `raiseToTop` 保住注记 |
| 易涝指数贴图 | `SingleTileImageryProvider` 贴一张 PNG，四角是透明像素（等经纬度矩形里套高斯-克吕格梯形） |
| 时间轴回放 | 153 帧按需加载：`frameCache` 只留当前帧 ±1，淘汰时 `remove(layer, true)` 连带销毁贴图；滑块 70 ms 防抖。实测同时在显存里的图层最多 5 个（全开会要 1.6 GB） |
| 点击查询 | 屏幕坐标 → 经纬度 → 网格行列 → 读 16 字节，返回指数/高程/坡度/汇流 + 等级 |
| 框选统计 | 拖框 → 行列窗口 → 按行分块读 → 各等级面积与占比（面积逐格按纬度换算，不用常数） |
| 易涝点 | 40 个区按等级着色 + 恒定屏幕尺寸的针尖（顶点笛卡尔坐标求平均定位置） |

点击查询有三种返回：`ok` / `no_data`（在水体或市域外）/ `outside`（超出 DEM 范围），
三种都是 HTTP 200——「点到没数据的地方」是正常交互，不是服务器错误。

## 七、已知局限

| 问题 | 影响 | 下一步 |
|---|---|---|
| DEM 是 DSM，含建筑与树冠 | 城区高程、坡度系统性偏高，中心区被低估 | 换 DTM，或用建筑掩膜剔除 |
| < 1.0 km² 的坑塘不剔 | 鱼塘、藕塘、院子围合的小坑算作陆地（武汉坑塘约 1,100 km²，绝大多数单块不足 1 km²） | 引入 WorldCover 10 m |
| 权重无实测标定 | 只能给相对排序，不能给绝对概率 | 收集真实渍水点做 logistic 回归 |
| 边界坐标系存疑 | DataV 边界可能是 GCJ-02，与 CGCS2000 有 300~500 m 偏差 | 核实后决定是否纠偏 |
| 排水管网缺失 | 汉口地面低于江面却靠泵站排干，纯地形算不出来 | 引入管网/泵站数据 |
| 1 个易涝点判不出来 | 南湖路供销学校落在 172 km² 的「汤逊湖 + 周边同高程平地」连通域里，地形上与湖面同构 | 换真实水面矢量（JRC Global Surface Water） |

第七条之外还有一条方法论上的：这个模型回答的是「哪里地形上更容易积水」，
不是「某年某月某日哪里真的积了水」。后者需要实测渍水记录做验证，本项目只做到
「官方高风险组的地形得分显著高于中风险组」这一级（均值 0.502 vs 0.364，
全城分位中位 84.9% vs 64.5%）。

| 接口 | 说明 |
|---|---|
| `GET /api/health` | 数据库连通、PostGIS 版本、易涝点计数 |

渲染与交互逻辑一行没改。

## 九、怎么跑

**开发模式**

```bash
cd backend && mvnw spring-boot:run      # 8080
cd frontend && npm run dev              # 5173，/api 代理到后端
```

浏览器打开 `http://127.0.0.1:5173`。**不要用 `localhost`**：天地图 key 的白名单只登记了
`127.0.0.1`，换成 `localhost` 会整片 403，现象是底图消失只剩一个蓝色地球。

**演示模式（不装 Node / Maven）**

```bash
scripts/build-demo.bat      # 打 release/（前端已进 jar）
scripts/启动演示.bat         # 双击起服务
```

只依赖本机 JDK 21 + PostgreSQL，数据库用 `sql/floodgis_demo.dump` 恢复。

**静态数据版（在线演示）**

线上托管只给一个静态目录，没有 JVM 也没有 PostgreSQL，所以另做了一份「无后端」构建：
`pipeline/publish/export_static.py` 把五个接口的返回导成文件，前端启动时按
`VITE_STATIC_DATA` 决定读接口还是读文件。

| 原接口 | 静态文件 | 体积 | 处理方式 |
|---|---|---|---|
| `/api/health` | `health.json` | 0.2 KB | 直接导出，`mode: "static"` 标明是快照 |
| `/api/zones` | `zones.geojson` | 52 KB | 直接导出 |
| `/api/admin` | `admin.geojson` | 76 KB | 直接导出 |
| `/api/flood-index` | `tiles/{tx}_{ty}.bin` | 21.5 MB / 196 块 | 四通道量化成 uint16，按 0.1° 分块，点哪块下哪块（单块 115 KB） |
| `/api/flood-index/stats` | `stats-index.bin` | 2.6 MB | 整幅索引、uint8 量化（1/254），一次下载后在浏览器里累加 |

```bash
cd pipeline && python publish/export_static.py   # 需要后端在跑（取三份 JSON）
cd frontend && npm run build:static              # 产物 dist/，任意静态服务器可托管
cd frontend && node scripts/verify-static.mjs    # 与后端逐格对账
```

两处容易踩的坑，都写在 `export_static.py` 的注释里：

1. **经纬跨度必须按 X/Y 分开算。** 外接矩形的跨度除以格数，两个方向算出来并不相等
   （1/1200 与 0.000833110），共用一个 `res` 会让同一点在后端和静态版落到相邻行，
   高程差十几米、等级都变。现在两边都写 `(east-west)/width`、`(north-south)/height`。
2. **框选统计不能降采样。** 4×4 块内只要有一个陆地格子就整块算有数据，等于把水体边缘
   填成低风险陆地，全市参与评价面积多算 10%。退回整幅分辨率、只把数值量化到 uint8，
   体积从 350 KB 涨到 2.6 MB，换来与后端一致的面积与分档。

核对结果：单点查询的行列号、等级完全一致（300 个随机点 + 5 个固定点，0 例不符）；
框选统计的 `cells / evaluated / no_data / area_km2 / mean` 与后端完全相同，
分档占比差 ≤0.5 个百分点，来源是索引被量化到 1/254 后个别格子跨了分级阈值。

**部署时踩到的第三个坑：天地图 key 绑域名。** 浏览器端 key 的域名白名单只有
`127.0.0.1`，换到线上域名后瓦片整片 403（响应体 `{"code":301007,"msg":"域名不匹配"}`），
Cesium 不报错、只是留白，页面看起来像"蓝色地球 + 一堆线"。
处理办法分两层：正确做法是去天地图控制台把线上域名加进白名单；
代码侧兜底是连续 6 块瓦片失败后自动把底图换成随包发布的 NaturalEarthII 离线影像
（`watchBaseMap()`），控制台同时给一条明确警告——不让它静默变成一个坏页面。

## 十、验证方式

| 环节 | 怎么验证 | 结果 |
|---|---|---|
| DEM 范围 | 与官方市域面积对比 | 8,573 vs 8,569 km²，差 0.0% |
| 分级阈值 | 反查分级面积是否等于分位比例 | 逐档相等 |
| 水体掩膜 | 5 个水面点 + 6 个陆地点人工核对 | 11/11 通过 |
| 易涝指数 | 与 40 个官方易涝点比对 | 39/40 有指数；官方高风险组均值 0.502、分位中位 84.9% |
| 敏感性 | 三套权重交叉比较 | 秩相关 0.968~0.998，顶档重合 67.4%~82.5% |
| 动态模型 | factor = 1 时是否严格还原静态指数 | 逐像元相等 |
| 前端贴图 | 上球后点位回查（山区红条、湖泊漏检） | 红条是滠水河谷；漏检已由 5.4 修掉 |
| 打包产物 | jar 内静态资源与 `frontend/dist` 逐项对齐 | 153 帧、0 张旧 png |
| 静态版一致性 | `frontend/scripts/verify-static.mjs` 与后端逐格对账 | 单点行列/等级 0 例不符；框选面积、均值全同，分档占比差 ≤0.5pp |
