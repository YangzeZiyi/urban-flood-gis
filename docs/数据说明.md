## 一、数据清单

### 1. 降雨数据

| 项 | 内容 |
|---|---|
| 产品 | **ERA5 再分析**（经 Open-Meteo Archive API 获取） |
| 用途 | 驱动风险模型、马尔科夫链、时间轴回放 |
| 接口 | `https://archive-api.open-meteo.com/v1/archive`，免费、无需 key |
| 站数 | 5 个虚拟站：汉口 WH01 / 武昌 WH02 / 汉阳 WH03 / 江夏 WH04 / 黄陂 WH05 |
| 时段 | **2017-01-01 ~ 2024-12-31**，每站 2,922 天日雨量 |
| 落库 | `rain_station` 5 行、`rain_record` 14,610 行（`data_source='open-meteo-era5'`） |
| 脚本 | `pipeline/fetch/fetch_rain.py`（带缓存、幂等入库） |

**为什么从 2017 年起，不从 2015：**

- 2015–2016 两年，四个城区站**逐日完全相同**（365/365、366/366）——那两年接口还是
  0.25° 粗网格，5 个点里 4 个落在同一格，"空间差异"是假的
- 2016-07-06 实况武汉国家站 246.4 mm、江夏 232.4 mm（中国气象局当日通报），
  这份数据只给 **44.4 mm**，削掉八成。ERA5 对"列车效应"这种中小尺度对流平滑得厉害

有这两条，2016 只能当背景故事讲，不能拿来验证模型。2017 起换成 0.1° 网格，
四城区站才真正分开。

**已知偏差：**

| 偏差 | 表现 | 影响 |
|---|---|---|
| 极端日削峰 | 2016-07-06 实测 246 mm → 数据 44 mm | 不能用于极端事件回放，只用于概率建模 |
| 格点非站点 | 数值是网格面平均，不是气象站观测 | 说"武汉下了 157 mm"可以，说"某某街道"不行 |
| 天气尺度 | 日雨量，无逐小时过程 | 做不了短历时强降雨的峰值分析 |

**校验值（重跑应该复现）：**

| 指标 | 值 | 说明 |
|---|---|---|
| 2017–2024 年平均 | 1,321 mm/年 | 武汉常年约 1,300 mm |
| 2020 年 | 2,024 mm | 超长梅雨，历史前列 |
| 最大日雨量 | 157.6 mm（2020-07-06，汉口） | 与气象局通报一致 |
| 暴雨日（≥50 mm） | 22 天 | 8 年累计，汉口站 |

**注意事项：**
- 免费 API 有调用次数限制，抓取要加延时
- 抓下来的原始 JSON 落 `data/raw/rain/`，避免重复请求；缓存按首尾日期校验，
  改了时间范围会自动重新下载
- 时间统一用本地时间，入库为 `TIMESTAMP` 不带时区；日雨量的 `obs_time` 记当天 00:00

### 2. DEM 高程数据

| 项 | 内容 |
|---|---|
| 产品 | **Copernicus DEM GLO-30**（欧空局 2020 发布） |
| 用途 | 计算坡度、填洼、汇流累积量、判定低洼区 |
| 来源 | AWS Open Data，免费、无需注册、无需 key |
| 地址 | `https://copernicus-dem-30m.s3.amazonaws.com/` |
| 格式 | GeoTIFF（COG，Deflate 压缩，带金字塔） |
| 格网 | 1 角秒 ≈ 赤道 30 m，武汉纬度约 26 m |
| 水平基准 | WGS84（EPSG:4326） |
| 垂直基准 | **EGM2008 大地水准面**（近似海拔，不是椭球高） |
| 单幅大小 | 1°×1°，3600×3600 像元，约 43~47 MB |
| 空洞值 | -32767（必须显式声明为 nodata） |
| 采集脚本 | `pipeline/fetch/fetch_dem.py` |

**为什么选它而不选 SRTM：**

- SRTM 是 2000 年航天飞机雷达数据，城区/植被区高程偏低（雷达只能打到树冠或屋顶），
  且高纬度有大量空洞需要插值
- Copernicus DEM 融合了 TanDEM-X 干涉测量，山区和城区的相对精度明显更好
- 两者都是 1 角秒格网，切换成本为零，没有理由用旧的

**武汉需要的分幅（9 幅）：**

```
N29_E113  N29_E114  N29_E115
N30_E113  N30_E114  N30_E115
N31_E113  N31_E114  N31_E115
```

> 武汉实际只占 113.70~115.08°E、29.97~31.36°N。
> N29 / E113 / E115 这几幅只沾了一点点边，但**必须下**——
> 少一幅，边缘就会出现一条空洞带，拼接后是一道 30 米宽的"悬崖"。

**处理流程（fetch_dem.py 做的四件事）：**

1. **分幅下载**：curl + 4 并发 + 断点续传（S3 按连接限速，单连接只跑 1 MB/s）
2. **拼接裁剪**：`rasterio.merge` 按武汉 bbox 只读相交窗口，不整幅载入
3. **重投影**：EPSG:4326 → **EPSG:4547**（CGCS2000 / 3 度带高斯-克吕格，中央经线 114°E）
4. **回查验证**：读回来算高程范围、有效像元比例，与官方特征比对

**关键概念：为什么必须重投影**

经纬度格网在物理上不是正方形：

| 位置 | 经度 1° 的实际距离 | 纬度 1° 的实际距离 |
|---|---|---|
| 赤道 | 111.3 km | 110.6 km |
| 30°N（武汉） | **96.5 km** | 110.6 km |

直接拿经纬度格网算坡度，等于把东西方向压缩了 13%，坡度、流向、汇流量全部失真。
投到高斯-克吕格平面后，格网是真 30 m × 30 m，这些量才有物理意义。

**为什么中央经线选 114°E**

中国 3 度带从 75°E 起，每 3° 一带，114°E 正好是一带中央经线，
且几乎穿过武汉市中心（114.3°E）。全境距中央经线最远 1.08°，
投影长度变形 < 0.02%，工程上可忽略。

> 常见错误：用 UTM 50N（EPSG:32650，中央经线 117°E）。
> 武汉西部 113.7°E 已经落在 UTM 49N 带内，跨带使用会带来额外变形。
> 国内项目正确做法是 3 度带高斯-克吕格 + CGCS2000。

**注意事项：**

- 文件较大（9 幅约 409 MB），不进 Git，`.gitignore` 已排除 `data/`
- 下载后按原始分幅留档，不要直接覆盖；重跑脚本会走缓存，只重做拼接
- 高程是 **EGM2008 正高**，不是 WGS84 椭球高，两者在武汉相差约 -10 m。
  做淹没分析时若与其他高程源混用，必须先统一垂直基准

### 4. 行政区边界

| 项 | 内容 |
|---|---|
| 用途 | 范围裁剪、统计分区、地图展示 |
| 来源 | **阿里云 DataV.GeoAtlas**：`https://geo.datav.aliyun.com/areas_v3/bound/420100_full.json` |
| 格式 | GeoJSON（MultiPolygon） |
| 坐标系 | WGS84（4326），与 DEM、天地图底图一致 |
| 规模 | 13 个区县，3341 个坐标点，80 KB |
| 入库表 | `admin_boundary`（PostGIS） |
| 采集脚本 | `pipeline/fetch/fetch_admin.py` |

`420100` 是武汉市的行政区划代码（42 湖北 / 01 市 / 00 本级），
末尾加 `_full` 表示连同下级区县一起返回。

**已做的质量核查：**

| 检查项 | 结果 |
|---|---|
| 区县数量 | 13，无重复 |
| 几何类型 | 全部 MultiPolygon，无空几何 |
| 面积交叉验证 | 13 区之和 = 市级 `ST_Union` = **8572.4 km²**（官方 8569，误差 0.04%） |
| 边界拓扑 | 各区无缝拼接，无重叠、无缝隙（面积和相等即证明） |

> 面积严格相等这一点很关键：如果区县之间有重叠，求和会**大于**市级面积；
> 如果有缝隙，求和会**小于**。两者相等，说明这组边界在拓扑上是干净的。

**注意：** 阿里云 DataV 的边界是**简化轮廓**（用于可视化，非测绘成果），
精度约百米级。做城市尺度的可视化足够，不能用于实际工程报批。

## 二、目录约定

实际使用的目录（`data/` 整个被 `.gitignore` 排除，不进仓库）：

```
data/
├── raw/                 原始数据，按来源分子目录，只增不改
│   ├── admin/           行政区边界 GeoJSON（wind: wuhan_420100_full.json）
│   └── dem/
│       └── copernicus/  9 幅原始 1°×1° 分幅，约 409 MB
└── processed/           处理产物，可随时由脚本重建
    └── dem/
        ├── wuhan_dem_4326.tif      拼接裁剪后，EPSG:4326
        ├── wuhan_dem_cgcs2000.tif  重投影后，EPSG:4547，30 m 米制格网
        └── wuhan_dem_meta.json     统计存档（范围、分辨率、高程分布）
```

**两条原则：**

1. **`raw/` 只增不改**——原始数据是唯一不可再生的东西，接口改版、链接失效都靠它兜底
2. **`processed/` 可随意删除**——它必须能由 `pipeline/` 里的脚本一键重建，
   否则说明你的处理过程没有固化下来，三个月后自己都复现不了

## 三、字段定义

### flood_zone（易涝风险区）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGSERIAL | 主键 |

| 字段 | 类型 | 说明 |

## 五、数据验证方法

做完易涝区提取后，用真实新闻验证：

1. 搜索"目标城市 + 暴雨 + 积水点"，找 2–3 个具体地点
2. 在 QGIS 或前端上把模型算出的高风险区叠上去
3. 看是否大致吻合

**不需要完全一致**，大致对得上就说明逻辑成立。这类项目的重点在链路完整与逻辑自洽，不在学术精度。

## 七、点击查询用网格（M4）

`data/processed/dem/` 下两个文件，由 `flood_index.py` 一并生成：

| 文件 | 内容 | 大小 |
|---|---|---|
| `wuhan_flood_index_grid.bin` | float32、行优先、4 通道交错 [index, elev, slope, acc]、小端 | 44 MB |
| `wuhan_flood_index_grid.json` | 宽高、经纬度范围、通道顺序、分级阈值 | 1 KB |

- 坐标：**EPSG:4326，3 角秒/格**（约 92 m 南北 × 77 m 东西），尺寸 1656 × 1671
- 取值：`offset = (row * width + col) * 16`，`row = (north - lat) / (north - south) * height`
- `index` 通道：水体与市域外一律 `NaN`（表示"不参与评价"，区别于"低风险"）
- 重新生成：`python pipeline/process/flood_index.py`（约 10 秒）
