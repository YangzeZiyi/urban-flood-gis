# 框选统计：从"拖一个框"到"这块地平均多危险"（M4）

> 点击查询回答的是"这一点怎么样"，框选统计回答的是"这一片怎么样"。
> 后者才是分析里更常用的动作：**选一个片区，看它的风险构成**。
> 这一篇涉及三个新东西：Cesium 的拖拽手势、Java 的分块读、按纬度变化的面积换算。

---

## 一、整条链路

```
按住左键拖动
   ↓  两个屏幕坐标（起点、终点）
Cesium 各自反算经纬度
   ↓  west, south, east, north
GET /api/flood-index/stats?west=..&south=..&east=..&north=..
   ↓
行列窗口 → 分块读 → 逐格累加
   ↓
{ 面积, 平均, 中位, 五档面积 }
```

和单点查询共用同一套"经纬度 → 行列号"的换算，区别只在：单点读 16 个字节，框选读一片。

## 二、三个事件拼成一个拖拽

Cesium 的 `ScreenSpaceEventHandler` 可以分别监听按下、移动、抬起：

```js
clickHandler.setInputAction(onDown, Cesium.ScreenSpaceEventType.LEFT_DOWN)
clickHandler.setInputAction(onMove, Cesium.ScreenSpaceEventType.MOUSE_MOVE)
clickHandler.setInputAction(onUp,   Cesium.ScreenSpaceEventType.LEFT_UP)
```

三件事必须做对，否则体验立刻崩：

**① 拖框时要把相机锁住。** Cesium 默认左键拖动是"转地球"，不锁的话你一边画框、地球一边转，框的位置全乱。

```js
viewer.scene.screenSpaceCameraController.enableInputs = false   // 按下时
viewer.scene.screenSpaceCameraController.enableInputs = true    // 抬起时，务必还回来
```

这行"还回来"漏掉一次，用户的地图就再也拖不动了，看起来像"卡死"。组件销毁时（`onBeforeUnmount`）也要再还一次。

**② 起点可能比终点更东、更北。** 直接拿 `start.lon` 当西边界，会得到"负宽度"的矩形——Cesium 不报错，只是什么都不画。

```js
const w = Math.min(start.lon, p.lon)
const e = Math.max(start.lon, p.lon)
```

**③ 拖完会多出一次 `LEFT_CLICK`。** Cesium 认为"按下又抬起"也是一次点击，于是刚统计完就弹出单点卡片。用时间戳挡掉：

```js
suppressClickUntil = performance.now() + 300
```

## 三、屏幕 → 经纬度 → 行列窗口

前端只负责把两个角点转成经纬度（`pickEllipsoid` + `Cartographic.fromCartesian`），**投影和取整全部交给后端**。理由和单点查询一样：同一套换算只写一次。

后端拿到 bbox 后：

```java
int c0 = colOf(west);   // 西边界 → 小列号
int c1 = colOf(east);
int r0 = rowOf(north);  // 北边界 → 小行号（第 0 行在最北）
int r1 = rowOf(south);
```

顺序是**北→小行、南→大行**，写反了统计到的是一片上下颠倒的区域，而且数字看起来完全正常。

边界要夹：`colOf` / `rowOf` 内部都做了 `clamp(0, width-1)`。用户可以把框拖到省外，不夹会数组越界。

## 四、为什么按行分块读

整幅数据 44 MB。全读进内存也能跑，但那是**每个请求 44 MB**，几个人同时框选就爆了。

做法是每次读 128 行（约 3.4 MB），在内存里扫完就丢：

```java
long offset = (long) rs * width * BYTES_PER_CELL;
while (buf.position() < want) {
    int got = channel.read(buf, offset + buf.position());
    ...
}
```

注意 `channel.read(buf, position)` 是**定位读**，不移动文件指针，多线程同时框选不会互相踩。

实测（本机，SSD）：

| 框选范围 | 格子数 | 耗时 |
|---|---|---|
| 汉口核心（8 km × 8 km） | 8,245 | **7 ms** |
| 半个市域 | 519,841 | **67 ms** |
| 整幅网格 | 2,766,696 | **242 ms** |

整幅 242 ms 里，一半时间花在把 44 MB 读进来，一半花在排序算中位数。

## 五、面积为什么不能用一个常数

网格按**经纬度**等分，不是按米。同样 1 度：

- 纬度方向：永远是 110.6 km
- 经度方向：赤道 111.3 km，30°N 只有 **96.4 km**（缩了 13%）

所以每个格子的面积随纬度变化。正确做法是**逐行算**：

```java
double cellKm2 = (dLat * 110.574)
               * (dLon * 111.320 * Math.cos(Math.toRadians(latRow)));
```

一根筋地用"平均格面积 × 格子数"，全市误差能到几十平方公里。

> 这也是个通用教训：**凡是"每格多大"的问题，先问坐标系是度还是米。**

## 六、NaN 不能当 0（本节的 TODO）

网格里 `index` 为 `NaN` 的格子，表示"不参与评价"——水体、市域外。

统计时必须**整格跳过**：

```java
if (Float.isNaN(v)) {
    noData++;
    continue;
}
```

两种偷懒写法都会错，而且错得不一样：

| 写法 | 后果 |
|---|---|
| 直接 `sum += v` | `sum` 变成 NaN，平均指数整个报废（页面显示「—」） |
| 当成 0 加进去 | 均值被拉低。框一半东湖，平均风险立刻"变安全" |

第二种更危险，因为它**不会报错**，只是悄悄给出一个偏向乐观的数。

还有第三个症状：`levelIndex(NaN)` 找不到任何区间（NaN 和谁比都是 false），会落到最后一档，于是"极高"面积暴涨——本次实测从 2.7% 涨到 17.8%。

**自检信号**（跑 `?west=114.24&south=30.55&east=114.32&north=30.62`）：

| 指标 | 正确 | 漏掉 NaN 判断 |
|---|---|---|
| 参与评价格子 | 6,965 | 8,245 |
| 无数据格子 | 1,280 | 0 |
| 平均指数 | 0.376 | `NaN`（显示「—」） |
| 极高占比 | 2.7% | 17.8% |

## 七、中位数与 p90

平均指数容易被极端值带偏，所以同时给中位数和 p90。

实现是"把所有有效值排一遍，取第 `round(q × (n-1))` 个"，**不做线性插值**：

```java
int i = (int) Math.round(q * (sorted.length - 1));
return sorted[i];
```

不插值是为了和 Python 基准**逐位对得上**。`numpy.quantile` 默认插值，两边会差千分之几——不是错，但对比时会被当成 bug 查半天。

## 八、验收：和 Python 基准逐位对齐

固定三个 bbox，用 Python 直接读同一个 `.bin` 算一遍，再和接口返回比：

| bbox | 格子 | 参与评价 | 面积 km² | 平均 | 中位 | 最高 |
|---|---|---|---|---|---|---|
| 114.24,30.55,114.32,30.62 | 8,245 | 6,965 | 51.243 | 0.376 | 0.343 | 0.969 |
| 114.32,30.50,114.42,30.58 | 11,737 | 11,737 | 86.392 | 0.406 | 0.397 | 0.945 |
| 113.9,30.2,114.5,30.8 | 519,841 | 410,031 | 3,018.934 | 0.408 | 0.375 | 0.975 |

**三组全部一位不差**，包括最高点坐标（114.278572, 30.607711）。

## 九、一个顺带查出来的问题

第二个 bbox（含东湖）返回 **无数据 0 格**——东湖一格都没被水体掩膜抓住。

原因还是那条老判据：`高程 ≤ 22 m 且坡度 < 0.1°`。东湖水面高程约 23~24 m，比阈值高一点点，整片湖被当成陆地参与了评价。

后果：东湖、南湖、沙湖这些 24~30 m 的湖，在统计里都算"高风险陆地"，会把片区的平均指数抬高。

修法两条（M5 待办）：

- 短期：`填洼深度 > 8 m 且坡度 < 0.1° 且汇流 > 5000`
- 正解：ESA WorldCover 10 m 地表覆盖的水体类，或 OSM 水面多边形

## 十、这个功能为什么值得写进简历

一句话：**"实现了基于随机访问栅格的区域统计，单次查询 O(N)，整幅 277 万格 240 ms 内返回。"**

它体现的能力比"点击弹窗"高一档：

- 知道**栅格不是数据库**，按坐标取数是偏移量计算
- 知道**面积要随纬度换算**，不是 `格子数 × 常数`
- 知道 **NaN 不是 0**，缺失数据不能参与统计
- 知道**分块读**，不让一个请求吃掉 44 MB 内存
