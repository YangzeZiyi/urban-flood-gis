## 零、先建立整体印象

我们做的不是一个"网页"，而是**四个程序互相配合**：

```
┌──────────────┐   ①HTTP请求    ┌──────────────┐   ②转发   ┌──────────────┐   ③SQL   ┌────────────┐
│   浏览器      │ ─────────────> │ Vite 开发服务器│ ───────> │ Spring Boot  │ ──────> │ PostgreSQL │
│  (Vue页面)    │ <───────────── │   :5173       │ <─────── │   :8080      │ <────── │  :5432     │
└──────────────┘   ④JSON返回    └──────────────┘           └──────────────┘          └────────────┘
       ↑                                                          ↑
   画地球/画易涝区                                          查 flood_zone 表
```

**四个程序分别是什么：**

| 程序 | 角色 | 类比 |
|---|---|---|
| 浏览器里的 Vue 页面 | 负责"显示"和"交互" | 餐厅服务员：接待客人、上菜 |
| Vite 开发服务器 | 负责把 `.vue` 编译成浏览器认识的 JS，并做转发 | 后厨传菜窗口 |
| Spring Boot | 负责业务逻辑、查数据库、返回 JSON | 厨师：做菜 |
| PostgreSQL + PostGIS | 负责存数据、算空间关系 | 仓库 + 冷库 |

**为什么要拆成前后端两个工程，不写一个？**
因为职责不同：前端改一次界面要重新打包、后端改一次接口要重启，混在一起互相拖累。分开之后，前端可以部署到 CDN，后端可以单独扩容。这是行业标准做法：前端可以单独部署到 CDN，后端可以单独扩容。

## 二、后端 · pom.xml（项目图纸）

### 2.1 Maven 是干什么的

Java 世界没有 `npm install`，用的是 Maven。它干三件事：

1. **管依赖**：声明"我要用 Spring Web"，它自动把 Spring Web 和它依赖的十几个 jar 全下下来
2. **管版本**：避免你写的 A 库和 B 库版本冲突
3. **管打包**：把代码 + 依赖打成一个能直接运行的 jar

`pom.xml` 就是它的配置文件。改完必须让 IDEA **重新加载**（右上角出现的刷新图标，快捷键 `Ctrl+Shift+O`），否则新依赖不会被下载。

### 2.2 三个坐标

```xml
<groupId>com.floodgis</groupId>          <!-- 组织/公司，反写域名 -->
<artifactId>floodgis-backend</artifactId> <!-- 项目名 -->
<version>0.0.1-SNAPSHOT</version>         <!-- 版本，SNAPSHOT = 开发中 -->
```

这三行合起来唯一确定一个工程，就像身份证号。将来打包成 jar，文件名就是 `floodgis-backend-0.0.1-SNAPSHOT.jar`。

### 2.3 parent：最省事的一行

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.16</version>
</parent>
```

**它的作用：帮你把依赖版本对齐。**

如果没有 parent，你得这样写：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <version>3.5.16</version>   <!-- 每个都要写，还得保证彼此兼容 -->
</dependency>
```

有了 parent，下面所有 `spring-boot-*` 和常用第三方库（Jackson、Hibernate、PostgreSQL 驱动）**都不用写版本号**，Spring 官方已经测过"哪几个版本配在一起不打架"。

> **为什么选 3.5.16 而不是最新的 4.1.x？**
> Spring Boot 4 是 2025 年底发布的大版本，改动不小（模块化拆分、Spring Framework 7）。网上 95% 的教程、B 站视频、Stack Overflow 答案还都是 3.x 语法。你现在正在重新熟悉生态，**先跟着主流版本走，遇到问题能搜到答案**。等这个项目做完，再花半天升级到 4.x 是很平滑的（注解基本没变）。

### 2.4 五个依赖，各管一块

| 依赖 | 管什么 | 少了它会怎样 |
|---|---|---|
| `spring-boot-starter-web` | 内嵌 Tomcat + Spring MVC + JSON 序列化 | 启动不了 Web 服务，`@RestController` 无效 |
| `spring-boot-starter-jdbc` | `JdbcTemplate`，手写 SQL 的工具 | 无法访问数据库 |
| `postgresql` | PostgreSQL 的 JDBC 驱动 | 报 `No suitable driver found` |
| `spring-boot-devtools` | 改代码自动重启 | 每次改完要手动点重启，效率减半 |
| `spring-boot-starter-test` | JUnit 5 测试框架 | 写不了单元测试 |

> **"starter" 是什么意思？**
> 它是一个"依赖套餐"。`spring-boot-starter-web` 里面其实包含了 spring-webmvc、tomcat、jackson 等十几个 jar。你写一行，等于点了整套套餐。

### 2.5 scope 是什么意思

```xml
<scope>runtime</scope>
```

声明"这个 jar 什么时候需要"：

| scope | 含义 | 例子 |
|---|---|---|
| （不写）= compile | 编译和运行都要 | Spring Web |
| `runtime` | 编译时不需要，运行时才要 | PostgreSQL 驱动（代码里不 import 它的类，但连库时必须存在） |
| `test` | 只有跑测试时需要 | JUnit |

### 2.6 打包插件

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>
```

它把项目打成**"胖 jar"**：你的代码 + 所有依赖 + 内嵌 Tomcat，全部塞进一个文件。上线时只要服务器装了 JDK，`java -jar xxx.jar` 就能跑，不用另外装 Tomcat——这是 Spring Boot 最讨喜的地方。

## 三、后端 · 启动类

```java
@SpringBootApplication
public class FloodGisApplication {
    public static void main(String[] args) {
        SpringApplication.run(FloodGisApplication.class, args);
    }
}
```

整个后端就 5 行，但 `@SpringBootApplication` 这一个注解干了三件事：

```
@SpringBootApplication
   ├── @SpringBootConfiguration   声明这是配置类（本质是 @Configuration）
   ├── @EnableAutoConfiguration   自动配置 ← 魔法都在这儿
   └── @ComponentScan             扫描本包及子包，把组件注册进容器
```

### 3.1 自动配置到底"自动"了什么

`SpringApplication.run()` 执行时，Spring 会去 classpath 里找 `spring-boot-starter-web` 带来的类：

- 发现有 Tomcat 的类 → 启动一个内嵌 Tomcat，监听 8080
- 发现有 Spring MVC 的类 → 启用 `@Controller` 注解解析
- 发现有 Jackson 的类 → 配置好 JSON 序列化器
- 发现有数据库驱动 + `application.yml` 里有 `datasource` → 建一个连接池

**这就是为什么你什么配置都没写，服务就能跑起来。** 传统 Spring 项目要写几百行 XML 才能达到同样效果。

### 3.2 main 方法里发生了什么

```java
SpringApplication.run(FloodGisApplication.class, args);
```

1. 创建 **IoC 容器**（一个巨大的 Map，存所有对象）
2. 扫描并实例化所有 Bean（`@Controller`、`@Configuration` 等）
3. 启动内嵌 Tomcat
4. **阻塞主线程**——所以程序不会退出，一直等着接请求

> 你按 `Ctrl+C` 或者在 IDEA 点红色方块，就是打断这个阻塞。

## 四、后端 · application.yml

### 4.1 YAML 语法（新手最容易踩）

```yaml
server:
  port: 8080
```

三条铁律：

1. **缩进表示层级**，只用空格，**绝对不能用 Tab**（这是 YAML 最常见的报错原因）
2. **冒号后面必须有空格**，`port:8080` 是错的，`port: 8080` 才对
3. 同一个层级缩进必须一致

### 4.2 数据库连接串怎么读

```yaml
url: jdbc:postgresql://localhost:5432/floodgis
```

拆开看：

```
jdbc:postgresql://  localhost  :  5432  /  floodgis
└── 协议 ────────┘  └主机┘     └端口┘     └库名┘
```

- `jdbc:` 是 Java 访问数据库的统一协议前缀
- `postgresql://` 告诉驱动"我要连 PG"（连 MySQL 就换成 `mysql://`）

### 4.3 密码那一行

```yaml
password: postgres    # ★★★ 改成你装 PostgreSQL 18 时设的密码 ★★★
```

这一行**不改，后端一定启动失败**，报错是：

```
org.postgresql.util.PSQLException: 致命错误: 用户 "postgres" Password 认证失败
```

改完保存，`devtools` 会在 3 秒内自动重启，不需要手动停服务。

### 4.4 HikariCP 连接池

```yaml
hikari:
  maximum-pool-size: 5
  connection-timeout: 5000
```

**为什么需要连接池？**
每次请求都新建一个数据库连接，要经历 TCP 三次握手 + 密码认证，几十毫秒就没了。连接池预先开好几条连接放在那儿反复用，请求来了直接取。

| 参数 | 作用 | 调优思路 |
|---|---|---|
| `maximum-pool-size` | 最多几条连接 | 开发机 5 条足够；生产一般是 CPU 核数 × 2 + 磁盘数 |
| `connection-timeout` | 等连接最多等多久 | 设 5 秒。默认 30 秒，数据库挂了接口会卡 30 秒才报错，很坑 |

### 4.5 日志级别

```yaml
logging:
  level:
    com.floodgis: DEBUG
    org.springframework.jdbc.core: DEBUG
```

日志级别从低到高：`TRACE < DEBUG < INFO < WARN < ERROR`。设成 DEBUG 就会输出这一级别及以上的日志。

`org.springframework.jdbc.core: DEBUG` 这一行特别有用：**它会把实际执行的 SQL 和参数打印出来**。以后接口查不出数据，先来这里看 SQL 长什么样，比瞎猜快十倍。

## 五、后端 · 跨域配置

### 5.1 同源策略是什么

浏览器有个安全规定：**协议 + 域名 + 端口，三者完全相同才算同源**。

| 页面地址 | 请求地址 | 是否同源 |
|---|---|---|
| `http://localhost:5173` | `http://localhost:5173/api` | ✅ 同源 |
| `http://localhost:5173` | `http://localhost:8080/api` | ❌ 端口不同 → 跨域 |
| `https://a.com` | `http://a.com` | ❌ 协议不同 → 跨域 |

跨域时，浏览器会先发一个 **OPTIONS 预检请求**问服务器"你允许我吗"。服务器不表态，真正的请求就不发出去，控制台报：

```
Access to fetch at 'http://localhost:8080/api/health' from origin 'http://localhost:5173'
has been blocked by CORS policy
```

### 5.2 两种解法，我们用了两种

**解法 A：后端声明允许（本文件做的事）**

```java
registry.addMapping("/api/**")
        .allowedOrigins("http://localhost:5173")
```

**解法 B：前端代理（vite.config.js 做的事，更常用）**

让 Vite 服务器把 `/api` 转发给 8080。浏览器全程只跟 5173 打交道，**根本不知道有跨域这回事**。

```
浏览器 ──/api/health──> Vite:5173 ──转发──> Spring:8080
         （同源，不查）                    （服务器之间没有同源限制）
```

> **为什么两个都写？** 代理在开发时最省事，但如果你直接用浏览器访问 `localhost:8080/api/health`，或者以后把前端部署到别的域名，CORS 配置就是保险。两者同时存在不冲突。

### 5.3 `@Configuration` 是什么

```java
@Configuration
public class WebCorsConfig implements WebMvcConfigurer {
```

- `@Configuration` 告诉 Spring："启动时加载我"
- `implements WebMvcConfigurer` 并重写 `addCorsMappings`，Spring MVC 启动时会回调这个方法，把规则注册进去

这是 Spring 的**扩展点**模式：框架留了一堆 `XxxConfigurer` 接口，你想改什么行为就实现哪个接口，不用改框架源码。

## 六、后端 · 健康检查接口

```java
@RestController
@RequestMapping("/api/health")
public class HealthController {
```

### 6.1 三个注解的作用

| 注解 | 作用 | 不写会怎样 |
|---|---|---|
| `@RestController` | 这个类每个方法都返回数据，自动转 JSON | 返回 404，或者 Spring 去找一个叫 `health` 的页面 |
| `@RequestMapping("/api/health")` | 类级别的 URL 前缀 | 路径变成根路径 `/` |
| `@GetMapping` | 这个方法处理 GET 请求 | 不被识别为接口 |

`@RestController` = `@Controller` + `@ResponseBody`。`@ResponseBody` 的意思是"把返回值直接写进 HTTP 响应体"，Spring 看到返回的是 `Map`，就用 Jackson 转成 JSON。

**访问地址就是这样拼出来的：**

```
类上的 @RequestMapping("/api/health")  +  方法上的 @GetMapping（无路径）
= GET http://localhost:8080/api/health
```

### 6.2 依赖注入：为什么没有 new

```java
private final JdbcTemplate jdbc;

public HealthController(JdbcTemplate jdbc) {
    this.jdbc = jdbc;
}
```

你可能会问：`new JdbcTemplate()` 在哪儿？

**答案是：不用你 new，Spring 已经 new 好了。**

流程是这样的：

1. 启动时，Spring 自动配置发现你有数据库配置 → 创建一个 `JdbcTemplate` 对象放进容器
2. 扫描到 `HealthController`，发现构造方法需要一个 `JdbcTemplate`
3. 从容器里找出那个对象，**塞进去**

这叫**构造器注入**，是官方推荐写法，好处：

- 字段可以是 `final`（不可变，线程安全）
- 依赖关系一目了然（看构造方法就知道这个类需要什么）
- 写单元测试时可以直接 `new HealthController(mockJdbc)`，不需要启动 Spring

> 老教程里常见 `@Autowired` 写在字段上，那是"字段注入"，现在不推荐：不好测试，而且可能掩盖循环依赖。

### 6.3 为什么要 try-catch 包住数据库查询

```java
try {
    String postgisVersion = jdbc.queryForObject("SELECT postgis_version()", String.class);
    ...
} catch (Exception e) {
    result.put("database", "DOWN");
    result.put("error", ...);
}
```

如果这里不捕获，数据库一挂，整个接口返回 **500 错误**。前端看到的就是一片红，**分不清是"后端没启动"还是"数据库连不上"**。

捕获之后，接口永远返回 200，但 body 里明确写着：

```json
{ "status": "UP", "database": "DOWN", "error": "PSQLException: Connection refused" }
```

一眼就知道"服务活着，是数据库的问题"。**这是排查问题的第一原则：把故障信息分级暴露，而不是一把糊掉。**

### 6.4 `queryForObject` 的两个参数

```java
jdbc.queryForObject("SELECT postgis_version()", String.class)
```

- 第一个参数：SQL
- 第二个参数：**期望返回什么类型**。这里期望一行一列、类型是 `String`

如果 SQL 返回多行，它会抛 `IncorrectResultSizeDataAccessException`。所以 `queryForObject` 只适合"确定只有一条"的查询。

## 七、后端 · 易涝区 GeoJSON 接口

### 7.1 接口签名

```java
@GetMapping
public Map<String, Object> listZones(@RequestParam(defaultValue = "1") int minLevel)
```

`@RequestParam` 从 URL 的 `?` 后面取值：

| 请求 | minLevel 的值 |
|---|---|
| `/api/zones` | `1`（defaultValue 生效） |
| `/api/zones?minLevel=3` | `3` |

`defaultValue = "1"` 让参数变成可选。不写的话，不传参就报 400。

### 7.2 SQL 里两个关键点

**① 占位符 `?` 而不是字符串拼接**

```java
String sql = "... WHERE risk_level >= ? ...";
jdbc.queryForList(sql, minLevel);
```

**绝对不能**写成 `"... WHERE risk_level >= " + minLevel`。因为如果 `minLevel` 来自用户输入，攻击者可以传 `1; DROP TABLE flood_zone` —— 这就是 **SQL 注入**。用 `?` 时，驱动会把参数当"纯数据"处理，不做任何语法解析。

**② `geometry::text` 这步在干什么**

```sql
geometry::text AS geojson
```

`v_flood_zone_geojson` 视图里的 `geometry` 列是 **json 类型**（PostGIS 的 `ST_AsGeoJSON()` 返回的）。如果直接 `get("geometry")`，Java 拿到的是 PostgreSQL 的 `PGobject`，不是字符串，处理起来别扭。

`::text` 是 PostgreSQL 的类型转换语法（等价于 `CAST(geometry AS text)`），把 json 转成字符串，Java 侧就是干净的 `String`，再用 Jackson 解析。

### 7.3 GeoJSON 是什么

**一句话：地图数据的通用语言。** 前端 Cesium、Leaflet、Mapbox 全认它，后端只要输出这个格式，换任何前端都不用改。

结构是固定的三层：

```json
{
  "type": "FeatureCollection",        ← 第一层：一组要素
  "features": [
    {
      "type": "Feature",              ← 第二层：一个要素
      "geometry": {                   ← 它"长什么样、在哪"
        "type": "Polygon",
        "coordinates": [[[114.3, 30.5], [114.4, 30.5], [114.4, 30.6], [114.3, 30.5]]]
      },
      "properties": {                 ← 它的"属性"（叫什么、多深、什么等级）
        "name": "武昌火车站下穿通道",
        "riskLevel": 4,
        "maxDepth": 0.85
      }
    }
  ]
}
```

**记住一句话：`geometry` 管画在哪儿，`properties` 管是什么。** 前端就是靠这两个字段分别渲染图形和弹窗。

> ⚠️ 坐标顺序是 **[经度, 纬度]**，不是 [纬度, 经度]。写反了地图上的点会跑到南极洲附近——这是 GIS 开发最经典的 bug。

### 7.4 `readTree` 为什么要用

```java
JsonNode geometry = objectMapper.readTree(geojsonText);
```

数据库给的字符串是：

```
{"type":"Polygon","coordinates":[[[114.3,30.5],...]]}
```

如果直接 `feature.put("geometry", geojsonText)`，最终 JSON 会变成：

```json
"geometry": "{\"type\":\"Polygon\",...}"     ← 字符串里套 JSON，前端解析不了
```

`readTree` 把字符串**解析成 JSON 树节点**，再放进去，Jackson 序列化时就会正常展开成对象。

### 7.5 为什么单条数据出错只跳过、不整体失败

```java
catch (Exception e) {
    System.err.println("[zones] 解析几何失败，id=" + row.get("id"));
    continue;
}
```

一个坏数据不该让整个接口 500。但也不能悄悄吞掉——所以要打日志，这样能定位到具体是哪条记录的 `id` 有问题。这是"**降级而非崩溃**"的思路。

## 八、前端 · package.json 与资源拷贝脚本

### 8.1 package.json 的结构

```json
{
  "type": "module",
  "scripts": { "dev": "vite", "build": "vite build" },
  "dependencies": { "cesium": "1.147.0", "vue": "3.5.45" },
  "devDependencies": { "vite": "7.3.8", "@vitejs/plugin-vue": "6.0.11" }

```

| 字段 | 含义 |
|---|---|
| `type: module` | 用 ESM 语法（`import/export`），而不是老的 `require` |
| `dependencies` | 运行时需要的包，会被打进最终产物 |
| `devDependencies` | 只在开发/打包时需要（Vite 本身、编译器），不进产物 |
| `scripts` | 命令别名。`npm run dev` 实际执行 `vite` |

**为什么版本号前面没有 `^`？**
本项目全部写死精确版本，好处是**任何人任何时间 npm install 装出来的都一样**，不会出现"昨天能跑今天不能跑"。等稳定了可以改成 `^` 允许小版本升级。

### 8.2 postinstall 钩子

```json
"postinstall": "node scripts/copy-cesium.mjs"
```

`postinstall` 是 npm 的生命周期钩子：**`npm install` 跑完会自动执行它**。

为什么要用它？看下一节。

### 8.3 Cesium 为什么需要单独拷资源

Cesium 不只是 JS 代码，它还带一批**运行时才去加载的非 JS 文件**：

| 目录 | 内容 | 少了会怎样 |
|---|---|---|
| `Assets/` | 贴图、离线底图、图标 | 球是黑的，或者底图 404 |
| `Widgets/` | 控件样式、按钮图片 | 缩放按钮变成一堆裸文字 |
| `Workers/` | Web Worker 脚本（几何计算在子线程跑） | 球转不动，控制台刷 404 |
| `ThirdParty/` | 第三方依赖（Draco 压缩等） | 加载 3D 模型失败 |

**Vite 打包器只处理代码**（`import` 进来的东西），这些文件不在 import 链里，所以必须原样放进 `public/` 目录。`public/` 里的东西会被**原封不动复制到构建产物根目录**。

脚本做的事：

```js
await cp(join(SRC, dir), join(DEST, dir), { recursive: true })
// node_modules/cesium/Build/Cesium/Assets  →  public/cesium/Assets
```

**为什么不用 `vite-plugin-cesium` 这个现成插件？**
那个插件最后一次更新很早，依赖的 `rollup-plugin-external-globals` 和 Vite 7 有兼容风险。二十行脚本解决的问题，不值得引入一个维护停滞的依赖——**能自己掌控的代码，比"能跑但不知道原理"的插件更可靠**。

## 九、前端 · vite 配置与 index.html

### 9.1 Vite 是什么

**Vite = 开发服务器 + 打包工具**，角色相当于 Java 那边的 Maven：

| 命令 | 作用 | 什么时候用 |
|---|---|---|
| `npm run dev` | 启动开发服务器，改代码浏览器毫秒级热更新 | 写代码时 |
| `npm run build` | 打包压缩，产物在 `dist/` | 部署上线时 |

它比老一代的 Webpack 快，因为开发时不打包——浏览器要哪个文件就现编译哪个。

### 9.2 代理配置（本项目最关键的一段）

```js
proxy: {
  '/api': {
    target: 'http://localhost:8080',
    changeOrigin: true,
  },
}
```

**过程还原：**

1. 前端代码写 `fetch('/api/health')`
2. 浏览器实际请求 `http://localhost:5173/api/health`
3. Vite 发现路径以 `/api` 开头，**在服务器端**转发给 `http://localhost:8080/api/health`
4. 拿到结果原样返回给浏览器

**好处有两个：**

- **没有跨域问题**：浏览器全程只跟 5173 打交道
- **上线不用改代码**：生产环境用 Nginx 配同样的转发规则，前端代码一个字都不用动

`changeOrigin: true` 的作用是把请求头里的 `Host` 改成目标地址，某些服务器会校验这个头，不加可能被拒。

### 9.3 index.html 里那行 script 为什么必须放最前面

```html
<script>
  window.CESIUM_BASE_URL = '/cesium/'
</script>
```

Cesium 运行时要知道去哪儿加载 `Assets`、`Workers`。默认它会按"根路径"找，但我们的资源在 `/cesium/` 下，所以要先告诉它。

**为什么不能用 `import` 写？**
因为 ES 模块的 `import` 会被**提升**（hoisting）——不管写在文件第几行，都先于其他语句执行。如果写成：

```js
import * as Cesium from 'cesium'   // 这一行先跑，Cesium 初始化时读到的还是旧路径
window.CESIUM_BASE_URL = '/cesium/'
```

路径就失效了。用一个普通 `<script>` 标签（非 module），它会在 module 脚本之前执行，顺序就对了。

> 这种"看起来无关紧要、实际决定成败"的细节，就是踩过一次就永远记住的经验。

## 十、前端 · main.js 与 App.vue

### 10.1 main.js 只有三行有效代码

```js
createApp(App).mount('#app')
```

- `createApp(App)`：用根组件 `App.vue` 创建一个应用实例
- `.mount('#app')`：把它挂载到 `index.html` 里 `<div id="app">` 的位置

**Vue 的核心思路：你不再手动操作 DOM。** 以前写 jQuery 要 `$('#x').text('hello')`，现在只要改变量，Vue 自动更新页面。

### 10.2 `<script setup>` 是什么

```vue
<script setup>
import { ref, computed, onMounted } from 'vue'
const health = ref(null)
</script>
```

这是 Vue 3 的语法糖，等价于老写法的 `setup()` 函数 + `return` 一大堆。它的好处：

- 里面定义的变量、函数、导入的组件，**模板里直接就能用**，不用注册、不用 return
- 代码更短，IDE 提示更准

### 10.3 三个核心 API

| API | 作用 | 例子 |
|---|---|---|
| `ref(初值)` | 创建**响应式**变量。值变了，页面自动更新 | `const health = ref(null)`，读写要用 `.value` |
| `computed(fn)` | **派生**状态。依赖变了自动重算，且有缓存 | 状态文案、颜色类名 |
| `onMounted(fn)` | 组件挂载到页面**之后**执行 | 初始化地图、发请求 |

**`.value` 的坑：** 在 JS 里必须写 `health.value`，在模板里写 `health`（Vue 自动解包）。这是新手最容易报错的地方。

### 10.4 为什么用 `computed` 而不是普通函数

```js
const statusText = computed(() => {
  if (loading.value) return '检测中…'
  ...
})
```

`computed` 会**缓存**：依赖（`loading`、`error`、`health`）没变时，多次访问直接返回上次结果，不重新计算。模板里每次渲染都调用的话，普通函数会重复执行，`computed` 不会。

### 10.5 模板里的指令

| 写法 | 含义 |
|---|---|
| `:class="statusClass"` | 冒号 = 绑定**变量**，不是字符串 |
| `@click="checkHealth"` | @ = 绑定事件 |
| `{{ health?.zoneCount ?? '—' }}` | 插值。`?.` 是空值保护，`??` 是"左边是 null/undefined 就用右边" |
| `v-if` / `v-else` | 条件渲染（元素不存在） |
| `ref="container"` | 把 DOM 元素存进同名变量 |
| `:disabled="loading"` | 加载中禁用按钮，防止连点 |

**`v-if` 和 `v-show` 的区别：** `v-if` 是真的把元素从 DOM 里删掉，`v-show` 只是加 `display:none`。频繁切换用 `v-show`，一次性的用 `v-if`。

### 10.6 `scoped` 样式

```vue
<style scoped>
```

加了 `scoped`，样式只作用于当前组件（Vue 会给元素加一个唯一属性做隔离）。不加就是全局样式，容易互相污染。

但 Cesium 是**动态生成**的 DOM，不受 scoped 约束，所以要用 `:deep()` 穿透：

```css
:deep(.cesium-viewer-bottom) { ... }
```

### 10.7 fetch 的错误处理为什么要写这么细

```js
try {
  const res = await fetch('/api/health')
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  health.value = await res.json()
} catch (e) {
  error.value = `连不上后端（${e.message}）。检查 IDEA 里后端是否在跑，端口 8080。`
}
```

两个容易忽略的点：

1. **`fetch` 只有网络层失败才 reject**。后端返回 404、500 时，`fetch` 是**成功**的，必须自己检查 `res.ok`
2. 浏览器对连接失败只报 `Failed to fetch`，对新手毫无信息量，所以要翻译成人话

## 十一、前端 · CesiumViewer.vue（核心）

这个文件是整个项目的地基，**后面加载易涝区、雨量站、水深，都是照这个骨架加东西**。

### 11.1 构造 Viewer

```js
viewer = new Cesium.Viewer(container.value, {
  baseLayer: Cesium.ImageryLayer.fromProviderAsync(...),
  animation: false,
  timeline: false,
  ...
})
```

`Viewer` 是 Cesium 的"总控台"，它内部创建了：

- **Scene**：三维场景（相机、光照、地球）
- **Camera**：相机（控制视角）
- **Canvas**：WebGL 画布（真正干活的地方）
- **各种控件**：缩放按钮、时间轴、底图切换器

**那一堆 `false` 是在关掉默认控件**。Cesium 默认把所有控件全开，界面又花又慢，而且 `geocoder` 默认走 Bing（国内用不了），`baseLayerPicker` 会去连 Ion 服务器（要 token）。关掉之后清爽很多。

### 11.2 底图：为什么用离线的

```js
baseLayer: Cesium.ImageryLayer.fromProviderAsync(
  Cesium.TileMapServiceImageryProvider.fromUrl(
    Cesium.buildModuleUrl('Assets/Textures/NaturalEarthII'),
  ),
)
```

拆解：

- `buildModuleUrl` → 根据 `CESIUM_BASE_URL` 拼出 `/cesium/Assets/Textures/NaturalEarthII`
- `TileMapServiceImageryProvider.fromUrl` → 读这个目录里的 `tilemapresource.xml`，按 TMS 规则加载瓦片
- `ImageryLayer.fromProviderAsync` → **把 Promise 包成图层**（因为 `fromUrl` 是异步的）

**为什么用这个而不是在线高清影像？**
因为它**不需要 token、不需要联网、装完就能看到球**。第一周的目标是"确认三维环境通了"，不是一个漂亮的底图。等链路验证完，再换天地图或 Ion（代码末尾注释里写了三种换法）。

> ⚠️ 里面特别标注了高德：它是 **GCJ-02 火星坐标**，和我们的 WGS84 数据有几百米偏移。**正式成果绝对不能用**，只能拿来做演示。这是 GIS 行业的基础常识。

### 11.3 相机定位

```js
viewer.camera.setView({
  destination: Cesium.Cartesian3.fromDegrees(114.305, 30.593, 26000),
  orientation: { heading: 0, pitch: Cesium.Math.toRadians(-90), roll: 0 },
})
```

- `fromDegrees(经度, 纬度, 高度米)` → 转成 Cesium 内部用的**笛卡尔坐标**（地心三维坐标）。为什么不直接用经纬度？因为地球是球，三维计算必须用直角坐标系
- `pitch: -90°` → 垂直俯视地面。0 是平视，-90 是正上方往下看
- `heading`：朝向，0 = 正北
- `roll`：翻滚（一般不用，除非做飞行模拟）

### 11.4 Entity：Cesium 的业务对象

```js
viewer.entities.add({
  id: 'demo-wuhan',
  name: '武汉市',
  position: Cesium.Cartesian3.fromDegrees(...),
  point: { pixelSize: 10, color: ..., heightReference: CLAMP_TO_GROUND },
  label: { text: '武汉', ... },
})
```

**Entity 的思维模型：一个 Entity = 地图上的一个对象 + 它的所有外观。**

一个 Entity 可以同时挂多种外观：

| 外观 | 效果 |
|---|---|
| `point` | 画一个点 |
| `label` | 加文字标注 |
| `billboard` | 贴图标 |
| `polyline` | 画线 |
| `polygon` | 画面 |
| `model` | 加载 3D 模型（glTF） |

**它们共享同一个 `position`**，所以点和文字会在一起——这就是为什么不用加两个 Entity。

`heightReference: CLAMP_TO_GROUND` 的意思是"贴地"，不加的话点可能悬在半空或被地形挡住。

### 11.5 最关键的坑：onBeforeUnmount 必须 destroy

```js
onBeforeUnmount(() => {
  if (viewer && !viewer.isDestroyed()) {
    viewer.destroy()
  }
})
```

**不写会怎样？**
Cesium 占用大量 GPU 显存。Vite 热更新时组件会销毁重建，如果旧 viewer 没释放，**改十次代码就吃掉几个 G 显存**，浏览器标签页直接崩。

`viewer.isDestroyed()` 这个判断是防御性的：避免重复 destroy 抛异常。

> 这个问题在 Cesium + Vue/React 项目里极其常见，网上大量"内存泄漏"帖子都是这个原因。

### 11.6 一个反直觉的坑：贴地多边形没有描边

这是我们在画武汉 13 个区边界时**实际踩到**的坑，值得单独记一节。

**错误写法（看着很合理，但什么都不显示）：**

```js
const admin = await Cesium.GeoJsonDataSource.load('/api/admin?level=district', {
  clampToGround: true,
  fill: Cesium.Color.TRANSPARENT,      // 不要填充
  stroke: Cesium.Color.CYAN,           // 只要青色描边
  strokeWidth: 1.5,
})
```

**结果：屏幕上一条线都没有。** 既没填充也没描边，等于这层数据白加了。

**原因在 Cesium 源码里**（`GeometryVisualizer`，画多边形的那个类）：

```js
if (!onTerrain && defined(geometry.outline) && geometry.outline.getValue(time)) {
  //                     ↑ 只有「不贴地」的多边形，才会创建描边图元
  const outlineInstance = this._geometryUpdater.createOutlineGeometryInstance(time)
  ...
}
```

`onTerrain` 就是「这个多边形是不是贴地」。贴地 = 走 `GroundPrimitive`，而 `GroundPrimitive` 这条路**根本没有描边实现**——它只把面"贴"在地形/影像上，边缘没有几何体可以画线。

所以规律是：

| 写法 | 填充 | 描边 |
|---|---|---|
| `clampToGround: true` + `fill` | ✅ 有 | ❌ 无（被忽略） |
| `clampToGround: false` + `fill + outline` | ✅ 有 | ✅ 有 |
| 贴地折线 `GroundPolylinePrimitive` | — | ✅ 有 |

**正确做法：边界用「贴地折线」画，不用多边形描边。**

```js
// 1. 把每一圈坐标取出来，转成扁平的 [经, 纬, 经, 纬, ...]
const flat = []
for (const [lon, lat] of ring) flat.push(lon, lat)

// 2. GroundPolylineGeometry = 会贴着地形走的线
const instance = new Cesium.GeometryInstance({
  geometry: new Cesium.GroundPolylineGeometry({
    positions: Cesium.Cartesian3.fromDegreesArray(flat),
    width: 2,          // 注意：单位是「屏幕像素」，不是米
  }),
  attributes: {
    color: Cesium.ColorGeometryInstanceAttribute.fromColor(lineColor),
  },
})

// 3. 所有线合成一个 primitive，只提交一次绘制
viewer.scene.primitives.add(new Cesium.GroundPolylinePrimitive({
  geometryInstances: allInstances,
  appearance: new Cesium.PolylineColorAppearance(),
}))
```

**顺带解释「为什么 20 条线只建一个 primitive」：**
每建一个 primitive 就是一次 draw call（CPU 通知 GPU 画一批东西）。20 个 primitive 就是 20 次来回，数据一多就掉帧。合成一个 primitive、内部放 20 个 `GeometryInstance`，**只要 1 次 draw call**。这是 Cesium 性能优化的第一原则：**能合批就合批**。

### 11.7 为什么 `flyTo(数据源)` 会飞得过头

```js
await viewer.flyTo(admin, { duration: 1.5 })   // 视野宽到能看见荆门、黄石
```

`flyTo` 传数据源时，内部做的是「算包围球 → 退到某个距离 → 带 45° 俯角看过去」。它考虑的是"能装下这个球"，不是"刚好装满屏幕"，所以实际视野会明显大于数据范围，还带一个斜角。

**想要精确框选，用 `Rectangle`：**

```js
const PAD = 0.05   // 四周留 5% 余量
await viewer.camera.flyTo({
  destination: Cesium.Rectangle.fromDegrees(
    west - PAD, south - PAD, east + PAD, north + PAD,
  ),
  duration: 1.5,
})
```

传 `Rectangle` 时，Cesium 会反算出一个高度，让这个经纬度矩形**正好铺满视口**，而且是正俯视。做"全省/全市概览"这类固定视野时，这个比 `flyTo(数据源)` 可控得多。

> `Rectangle.fromDegrees` 的参数顺序是 **西、南、东、北**（west, south, east, north），不是常见的"左上右下"。记错了会得到一个空矩形。

### 11.8 后面要接着做什么

现在有一个点、13 个区的边界、一块易涝区。下一步（第二～三周）就是：

1. `fetch('/api/zones')` 拿到 GeoJSON
2. `Cesium.GeoJsonDataSource.load(geojson)` 一行加载

4. 点击时读 `properties` 弹信息框

**骨架已经搭好了，剩下都是"往 entities / primitives 里加东西"。**

### 11.9 把栅格算出来的结果铺到地球上（贴图）

前面 11.1~11.6 处理的都是**矢量**：点、线、面。但 M2/M3 算出来的坡度、汇流、易涝指数是**栅格**——一张 4440×5162 的网格，2268 万个值。

**栅格不能转成矢量再上球。** 每个像元转一个矩形，就是两千多万个多边形，浏览器会直接崩。正确做法是：

> **把整张栅格渲染成一张 PNG，作为一个"影像图层"贴在经纬度矩形上。**

GPU 只画一个四边形。这就是 `SingleTileImageryProvider` 干的事。

```js
const [w, s, e, n] = meta.bbox_wgs84           // 顺序：西、南、东、北
const provider = new Cesium.SingleTileImageryProvider({
  url: '/overlay/wuhan_flood_index.png',
  rectangle: Cesium.Rectangle.fromDegrees(w, s, e, n),
  tileWidth: meta.size_px[0],                  // 必填，见下面的坑
  tileHeight: meta.size_px[1],
})
overlayLayer = viewer.imageryLayers.addImageryProvider(provider)
overlayLayer.alpha = 0.85                      // 半透明，透出底图
```

**四个必须知道的点：**

**① 影像图层的顺序 = add 的先后，index 0 在最底下。**

```
底图 img_w(0) → 指数贴图(1) → 注记 cia_w(2)
```

注记层一定要最后 add，否则地名会被半透明的贴图糊住。这与 `scene.primitives` 的规则一致：后加的盖在上面。

**② `tileWidth` / `tileHeight` 在 1.147 里是必填的，虽然文档写"可选"。**

源码里是 `Check.typeOf.number("options.tileWidth", ...)`，不传就抛：

```
DeveloperError: Expected options.tileWidth to be typeof number, actual typeof was undefined
```

而且必须等于 PNG 的真实像素尺寸，否则贴图会被拉伸。

**③ 一张图铺满 = 缩放会糊。**

`SingleTileImageryProvider` 永远只有一个层级，整张图当一张纹理用。我们的贴图是 1110×1291（每像素 120 m），缩放到街道级就开始发虚。要看清必须切瓦片（TMS/XYZ），那是后续的事。**先用单图把链路跑通，再优化分辨率**，这个顺序别搞反。

**④ bbox 和分级阈值从 JSON 读，前端一个数字都不手抄。**

`pipeline/process/flood_index.py` 出图时会同时写一份 `wuhan_flood_index.json`：

```json
{
  "bbox_wgs84": [113.702281, 29.969132, 115.082378, 31.36126],
  "levels": [{ "name": "极高", "lo": 0.7272, "hi": 1.001, "color": "#f85149" }, ...],
  "weights": { "elev": 0.2, "slope": 0.15, "fill": 0.15, "acc": 0.5 }
}
```

前端拿它渲染图例。这样你改了权重、重跑脚本，**图例自动跟着变**。如果前端手抄一遍，一定会有一次忘了改，然后出现"图例说 0.73 才算极高，地图上 0.70 就红了"这类问题——查起来极痛苦。

> 这叫**单一数据源（single source of truth）**：同一个数字只在一个地方定义，其他地方都是引用。

**⑤ 贴图失败不该让整页白屏。**

整个加载过程包在 `try/catch` 里：贴图挂了，底图、区界、易涝区还能用，只是少了指数。控制台留一条明确的错误，比什么都看不见强。

## 十二、一次请求的完整链路

以打开页面为例，把所有环节串起来：

```
1. 你在浏览器打开 http://127.0.0.1:5173
   ↓
2. Vite 返回 index.html（里面有 CESIUM_BASE_URL、CSS、main.js）
   ↓
3. main.js 执行 → 创建 Vue 应用 → 渲染 App.vue
   ↓
4. App.vue 里 onMounted 触发 → fetch('/api/health')
   ↓
5. 请求发到 5173 → Vite 的 proxy 转发到 8080
   ↓
6. Spring Boot 的 DispatcherServlet 收到请求
   ↓
7. 按 URL 匹配到 HealthController.health()
   ↓
8. 方法里调 jdbc.queryForObject("SELECT postgis_version()")
   ↓
9. HikariCP 从连接池取一条连接 → 发给 PostgreSQL
   ↓
10. PG 执行函数 → 返回 "3.7.0 USE_GEOS=1 ..."
   ↓
11. 结果一层层往上返回，Map 被 Jackson 转成 JSON
   ↓
12. 前端 res.json() 拿到对象 → health.value = 对象 → 触发响应式更新
   ↓
13. 面板上的「数据库 UP / PostGIS 3.7」自动变绿
```

**这条链路里任何一个环节断了，你会看到不同的现象：**

| 现象 | 断在哪 |
|---|---|
| 页面白屏，控制台 `Failed to import` | Vite 没启动 / 依赖没装 |
| 球是黑的，`404 /cesium/Assets` | 拷贝脚本没跑（`npm install` 提前中断） |
| 面板显示"连不上后端" | Spring Boot 没启动 / 端口不是 8080 |
| 面板显示"数据库 DOWN" | 密码错了 / PG 服务没开 |
| 面板显示 `PostGIS` 是 `—` | 数据库连上了，但没装 PostGIS 扩展 |

**会看这张表，你就能自己排 80% 的错。**

## 十四、自测题

先自己答，再看答案。

**Q1.** `@SpringBootApplication` 拆开是哪三个注解？`@ComponentScan` 默认扫描哪个范围？

**Q2.** 后端返回 404，但代码看着没问题。最可能的原因是什么？

**Q3.** 前端 `fetch('/api/health')` 为什么不用写 `http://localhost:8080`？如果部署到服务器，需要改代码吗？

**Q4.** GeoJSON 里 `coordinates` 数组的前两个数字是什么？写反了会怎样？

**Q5.** `onBeforeUnmount` 里不写 `viewer.destroy()` 会发生什么？

**Q6.** SQL 里为什么必须用 `?` 占位符，不能字符串拼接？

---

### 答案

**A1.** `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`。扫描范围是**启动类所在的包及其所有子包**（本项目是 `com.floodgis.*`）。

**A2.** ① Controller 不在扫描范围内（包路径不对）；② 类的 `@RequestMapping` 路径和方法路径拼起来跟你想的不一样；③ 没加 `@RestController` / `@GetMapping`。先看启动日志里的 `Mapped "{[/api/xxx]}"` 确认路径到底注册成了什么。

**A3.** 因为 `vite.config.js` 配了 proxy，Vite 服务器转发给 8080，浏览器看来是同源。部署时**不用改代码**，只要 Nginx 配同样的 `/api` 转发规则。

**A4.** 第一个是**经度（longitude）**，第二个是**纬度（latitude）**。写反了点的位置会错到地球另一侧（武汉 latitude 30.6 会被当成经度）。

**A5.** GPU 显存不释放。热更新几次后显存吃满，标签页崩溃或整个浏览器卡死。

**A6.** 用 `?` 时驱动把参数当**纯数据**处理；字符串拼接会让用户输入参与 SQL 语法解析，攻击者可注入 `1; DROP TABLE ...` 删库。
