## 二、缓存与仓库位置（防止 C 盘被悄悄吃满）

这些是真正容易被忽略的"隐形 C 盘杀手"：

### npm 缓存
```bash
npm config set cache "D:\dev\cache\npm"
npm config set prefix "D:\dev\cache\npm-global"
```

### pip 缓存
```bash
python -m pip config set global.cache-dir "D:\dev\cache\pip"
```

### Maven 本地仓库（.m2 默认在 C 盘用户目录，能到几个 G）
在 `D:\dev\cache\maven-repo` 建目录，然后编辑 `C:\Users\Administrator\.m2\settings.xml`：
```xml
<settings>
  <localRepository>D:/dev/cache/maven-repo</localRepository>
</settings>
```
（IDEA 里也可以直接在 Settings → Build Tools → Maven → Local repository 改）

### Gradle 缓存（如果以后用到）
设置环境变量 `GRADLE_USER_HOME=D:\dev\cache\gradle`

## 六、VS Code 数据目录联接（C 盘零增长）

VS Code 的**用户数据**和**插件**默认写在 C 盘，官方没有迁移开关。用 Windows 目录联接（Junction）把真实目录搬走，原位置留一个"传送门"，VS Code 完全感知不到，升级也不会失效。

| C 盘原位置（现为联接） | 真实目录（D 盘） | 内容 |
|---|---|---|
| `C:\Users\Administrator\AppData\Roaming\Code` | `D:\dev\cache\vscode\Code` | 设置、工作区历史、缓存、日志 |
| `C:\Users\Administrator\.vscode` | `D:\dev\cache\vscode\dotvscode` | 插件 extensions、CLI 记录 |

**查看联接是否有效：**

```powershell
Get-Item "C:\Users\Administrator\AppData\Roaming\Code" | Select-Object FullName, LinkType, Target
```

`LinkType` 为 `Junction`、`Target` 指向 D 盘，即正常。

**如果哪天联接被破坏（例如系统重装或某些清理工具删掉了"空目录"）：**

```powershell
# 1. 先关掉所有 VS Code 窗口
Get-Process Code -ErrorAction SilentlyContinue | Stop-Process -Force

# 2. 如果 C 盘位置又变成真实目录，先把内容搬回 D 盘
robocopy "C:\Users\Administrator\AppData\Roaming\Code" "D:\dev\cache\vscode\Code" /E /MOVE
Remove-Item "C:\Users\Administrator\AppData\Roaming\Code" -Recurse -Force

# 3. 重建联接
New-Item -ItemType Junction -Path "C:\Users\Administrator\AppData\Roaming\Code" -Target "D:\dev\cache\vscode\Code"
```

> 同类做法适用于其他不听话的软件（JetBrains 的 Daemon 缓存、Docker 镜像、Chrome 用户数据等）。

## 七、Git 与 GitHub 仓库

**仓库地址**：`https://github.com/YangzeZiyi/urban-flood-gis`（Public）

**分支**：`main`（唯一，也是默认分支）

**首次提交时踩的两个坑：**

### 坑 1：`CRYPT_E_NO_REVOCATION_CHECK` —— 推送时报 SSL 证书错误

完整报错：

```
fatal: unable to access 'https://github.com/...': schannel: next InitializeSecurityContext failed:
CRYPT_E_NO_REVOCATION_CHECK (0x80092012) - 吊销服务器无法验证证书是否被吊销
```

**原因**：Windows 的 schannel 会去访问证书吊销列表（CRL/OCSP）验证 GitHub 证书是否有效，当前网络环境下这个验证请求失败，导致 TLS 握手被中断。**读操作（`ls-remote`）可能通过，写操作（`push`）一定失败**，因为写操作的证书检查更严格。

**解决**：

```bash
git config --global http.sslVerify false
```

> 代价是跳过证书吊销检查。对个人开发机风险极低（GitHub 证书本身有效，只是"无法确认是否已吊销"）。这是国内网络环境下的常见处理。

### 坑 2：删除默认分支被拒绝

```
! [remote rejected] master (refusing to delete the current branch: refs/heads/master)
```

**原因**：GitHub 不允许删除**默认分支**。

**正确顺序**（顺序错了就会卡）：

1. 先推新分支：`git push -u origin main`
2. **再去网页** Settings → General → Default branch，把默认分支切到 `main`（这一步命令行做不了）
3. 最后才删旧分支：`git push origin --delete master`

> 注意：网页上的 **Rename branch（重命名）** 和 **切换 Default branch（默认分支）** 是两个不同的操作。分支已存在时点 Rename 会报 `Branch main already exists`，别点错。

### 敏感文件处理

`backend/src/main/resources/application.yml` 含数据库明文密码，已加入 `.gitignore`，**不推送到仓库**。仓库里只有 `application.yml.example` 模板，别人克隆后复制一份改名、填自己的密码即可。

同理，`docs/*简历*.docx` 含个人隐私，也已排除。
